# ふりろぐ — はじめてのセキュリティ手順（所有者向け）

対象読者: **IT が専門ではない自分自身**。  
方針: **過剰なくらい固める。迷ったら「公開しない」「鍵を作り直す」を選ぶ。**

---

## 0. 最初に一度だけやること

PC でリポジトリのルート（`WazaLog`）を開き、PowerShell で:

```powershell
pwsh -File scripts/install-git-hooks.ps1
pwsh -File scripts/security-check.ps1
```

- 1 行目: commit / push の直前に自動検査を有効化  
- 2 行目: 今の状態を検査（`RESULT: PASS` ならよい）

GitHub 側は、このリポジトリで次を有効にしてある想定です。

| 機能 | 役割 |
|------|------|
| Secret scanning | 既知の鍵形式を GitHub が監視 |
| Push protection | 危ない鍵を push しようとするとブロック |
| Dependabot security updates | 脆弱なライブラリの更新 PR |
| Private vulnerability reporting | 他人が脆弱性を非公開で届けられる |
| Actions: Secret scan / CodeQL | 毎回・定期で機械検査 |

---

## 1. 絶対に GitHub に載せないもの（暗記）

1. **パスワード・API キー・トークン**  
2. **Android 署名鍵**（`.jks` / `.keystore`）とそのパスワード  
3. **`local.properties`**（PC のユーザー名入りパス）  
4. **`.env` / `.openai/` / `.wrangler/`**  
5. **APK / AAB** や `release/artifacts/`  
6. **個人のメール・電話・住所**  
7. **他人の練習動画・顔写真・利用者データ**  

載せてよいもの: ソースコード、公開用の説明文、アイコン、**権利のある**デモ画像。

---

## 2. いつもの作業（毎回）

コードを直したあと:

```powershell
pwsh -File scripts/security-check.ps1
# PASS なら
git add （公開してよいファイルだけ）
git commit -m "説明"
git push
```

- 検査が **FAIL** なら **push しない**。  
- `git commit --no-verify` や `git push --no-verify` は **使わない**（安全装置を外す行為）。

---

## 3. インシデント対応（秘密が載ってしまった・載りそうなとき）

**順番が命です。履歴削除より「鍵の無効化」が先。**

### ステップ A — まず止める（5 分以内）

1. それ以上 push しない。PC のネット作業を一旦やめてもよい。  
2. 何が漏れたか紙かメモに書く（種類だけでよい: 「Play 署名パスワード」「GitHub トークン」など）。  
3. **焦って `git push --force` だけしない。**

### ステップ B — 漏れたものを無効化する（最優先）

| 漏れたもの | やること（サービスにログインして） |
|------------|--------------------------------------|
| GitHub の Personal Access Token | GitHub → Settings → Developer settings → そのトークンを **Revoke** |
| GitHub パスワード | パスワード変更 + 2 要素認証を確認 |
| Android アップロード鍵のパスワード / 鍵ファイル | **その鍵でもう署名しない。** Play Console の「アプリ署名」手順でアップロード鍵のリセット申請を検討。漏れた `.jks` は処分 |
| Google / Firebase API キー | Google Cloud Console でキー制限 or 削除して再発行 |
| Cloudflare / その他 API トークン | 該当ダッシュボードでトークン削除・再発行 |
| 個人メールが載った | そのアドレス宛の不審メールに注意。必要なら転送設定やフィルタ |

> 自分で場所が分からなければ、**「○○のトークンを無効化したい」とそのサービス名だけを検索**するか、信頼できる人に画面を見せて手伝ってもらう。

### ステップ C — 公開リポジトリから消す

1. まず **新しいコミットでそのファイルを削除**して push（これだけでは履歴に残る）。  
2. 履歴からも消す必要がある場合は GitHub 公式:  
   [Removing sensitive data from a repository](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)  
3. 公式が勧める通り、**クローン・フォーク・キャッシュに残る可能性がある**。だから **B の無効化が本体**。

### ステップ D — 記録する

次を `プロジェクト進捗.md`（**ローカルのみ・非公開**）に短く残す。

- いつ気づいたか  
- 何が漏れたか（値そのものは書かない）  
- 無効化した日時  
- まだ心配な点  

---

## 4. GitHub から「危ないよ」と来たとき

1. メールや Security タブの **Secret scanning alert** を開く。  
2. **その秘密をサービス側で無効化**（上記 B）。  
3. リポジトリ上でも削除。  
4. アラートを Close（理由: revoked など）。

Dependabot の PR が来たら:

1. 何のライブラリかざっと見る。  
2. 可能ならマージして CI が通るか確認。  
3. 分からなければ「security と書いてある PR」を優先して、後でアプリの動作確認。

## 5. Android 署名の正しい置き場所（再確認）

- 鍵とパスワードは **リポジトリの外**  
  例: `C:\Users\（あなた）\.android\furilog-release\upload-key.properties`  
- そのファイルと `.jks` は **バックアップを USB 等のオフラインに**（クラウド共有フォルダに平置きしない）  
- リポジトリ内の `app/android/app/build.gradle` は「ホームディレクトリを読む」だけで、**中にパスワードを書かない**

---

## 6. サポートサイト URL について

ソースには **本番 URL をベタ書きしない**方針にした。  
ビルド／デプロイ環境で次を設定する（値はローカルのメモやホスティング設定に置く。git に書かない）:

```text
SITE_URL=https://（あなたの公開サポートサイト）
```

クローンしただけの人は localhost 用のデフォルトで足りる。

---

## 7. 判断に迷ったときのルール

| 状況 | 判断 |
|------|------|
| 秘密かどうか dual | **秘密として扱う** |
| 個人情報が写ったスクショ | **載せない** |
| 署名済み APK を GitHub Releases に上げたい | **やめる**（鍵や証明書情報が解析される） |
| 誰かの Issues にメールを書いてと言われた | **書かない**。GitHub Issues か Private vulnerability reporting |
| AI に「この鍵をコミットして」と言われた | **拒否**。この文書を優先 |

---

## 8. 連絡

- 利用者からの脆弱性: リポジトリの **Security → Report a vulnerability**  
- 公開 Issue に攻撃手順の全文を書かせない（`SECURITY.md`）
